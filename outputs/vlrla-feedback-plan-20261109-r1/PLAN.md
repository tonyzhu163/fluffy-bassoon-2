# Does one deployment episode help a frozen VLA correct its next attempt?

Simulation study proposed November 9, 2026. Use native simulator rewards for source PPO, student histories, and deployment feedback on RoboCasa and RoboTwin. Measure success with the native task predicate. Flora belongs to future physical-robot testing. No compute reservation or launch is attached to this plan.

The scientific question is whether the *particular experience* of a previous attempt helps the policy choose a more successful next action. The [VLRLA reviews](https://openreview.net/forum?id=6ZrDl6noHg) raise three alternatives: a stronger offline policy, imitation of better actions later in a training sequence, and another chance to succeed by resampling. The [paper](https://arxiv.org/html/2610.19517v1#S5) reports 60.6% for the bridge and 60.8% for GRPO on six held-out tasks. Our benchmark should establish how much experience each method needs to reach its score.

## What to put in context

For each trial, specify what the new observation and instruction leave uncertain, what persists across resets, and which action would change if the robot knew it. A gripper calibration error can persist when an object's starting pose changes. A miss caused by an independent draw of motor noise may say little about the next attempt. Use ordinary benchmark logs to investigate which situation applies. The controlled drawer offset below lets us construct both useful and irrelevant histories deliberately.

Start with a short record of **what the robot saw, what it actually did, and what changed**. For a grasp, retain aligned wrist and scene views, measured gripper state and proprioception before and after closure/lift, the intervening executed commands, and the terminal outcome. Two misses can both earn zero while the images show opposite lateral errors. Recover event windows from public gripper commands and sensor timestamps. Compare this compact context to an equal-token uniform sample of the same episode on source development; keep raw time-aligned observations so the choice is reversible. Simulator object pose, hidden condition, teacher version and future query outcome stay outside the student input.

Collect examples in which similar query observations need different corrections. Randomize the persistent condition independently of scene and attempt index. Sample multiple feasible approaches under each condition and record consequences on successes and failures. In the drawer diagnostic, try left and right corrections from paired resets on source development to measure which one helps. At training time a qualified teacher can label the action at the actual query state, or the learner can compare observed returns for the alternatives it has tried. An improving global PPO curve is useful for AD, but it alone says little about whether a particular preceding failure predicts the next good action. Preserve whole trial and teacher-stream boundaries.

Before a large fit, compare a simple predictor of the better measured correction using current inputs alone versus current inputs plus the completed support. Hold out entire scenes. Then execute the correction it selects on fresh development resets alongside native retries and a fixed correction. This distinguishes three practical problems: previous attempts may contain little information, our tokens may discard it, or the frozen motor may lack the control authority to act on it. Record each result separately. If a simple correction rule works, keep it as a baseline for the learned bridge.

## 1. Start with one support episode on RoboCasa

Use the frozen KV-AD fit on **CloseToasterOvenDoor** to develop the readout. After five supports it had 23/50 successes with history versus 17/50 with reset. After one support it had 8/50 versus 15/50. On CloseFridge the five-support counts were 33/50 versus 34/50. These inspected cases motivate the experiment and stay in development. The [existing AD curves](../robocasa-three-task-kv-velocity-meta-20261105-r1/STAGE1-RESULT.md) and [separate DPT/DIT readout](../robocasa-kv-dpt-dit-readout-20261109-r1/PLAN.md) already cover the original cases.

Start every trial with empty memory. Run one real support episode, save public observations, delivered actions, reward and boundaries, and reset the environment for a separate query. Keep the nominal case and task condition fixed within this trial. Count every support success and failure. Branch all same-weight interventions from the **same completed support record**; replace, clear or mask only the input specified below. Pair the query reset and motor noise, and withhold query outcomes until scoring. Continue to update within-episode memory normally.

| Query condition | What it tests |
| --- | --- |
| Own history | Frozen candidate with its actual prior experience. |
| Other trial's history | Exchange complete records between randomly paired trials of the same task, matched on native outcome, duration band and attempt index. Preserve plausible observations, actions and labels. Compare to own history to measure the value of knowing *which* trial occurred. |
| Episode reset | Same fitted weights and attempt index, clear cross-episode memory. Measures reliance on any retained input. |
| Own history, reward masked | Change only the reward input. Keep observations, actions, episode boundary and timing identical. Use a missing-reward encoding seen during fitting or label the evaluation-only mask as a distribution-shift diagnostic. |
| Separately trained controls | Fit a memoryless bridge and a reward-blind recurrent bridge with the same motor, source streams, targets, model width, optimizer budget and selection rule as the full bridge. Give the memoryless bridge the attempt index so it can learn a schedule. The reward-blind bridge keeps visual evidence of success and failure. |
| Native SFT retries | Redraw policy noise, charge the same attempts, and record each query's outcome. Measures improvement available from another try. |

Make the matching rule and seeded donor assignment final on development data. Report pairing coverage and unmatched records by outcome. Include all trials in the own/reset, trained-control and native comparisons. If a failed-support subgroup is reported, define it by the common pre-intervention support outcome. An individual model's selected failures do not form a matched comparison to a different model's selected failures.

## 2. Test what a failure tells the policy

Use **OpenDrawer** for a separate handle-grasp diagnostic. Introduce a signed lateral offset into the simulator's end-effector command during approach. Randomize left/right equally between trials and keep it fixed through support and query. The policy sees its normal cameras, proprioception, instruction and native feedback. The evaluator alone records the imposed sign, handle pose and fingertip error.

On source-development scenes, verify that zero offset recovers the native path, that opposite offsets cause opposite miss directions, and that compensating the known offset improves grasp success. Choose a feasible magnitude there. Include both signs in source training, retain unmodified cases, and reserve a second magnitude and fresh scenes for transfer. Freeze the geometry, reference frame, grasp timestamp and missing-grasp scoring rule before the test.

After the same failed support, run three paired queries: own history, a donor failure with the same offset sign, and a donor failure with the opposite sign. Match donors on scene geometry and reward. Compare signed commanded displacement at the first grasp with the reset policy, then measure handle acquisition and native task success. A shift toward the correction with own and same-sign history, and toward the opposite side with opposite-sign history, is a prediction about *which action* the policy learns. A movement change without a success gain establishes sensitivity only. Report native, unmodified OpenDrawer separately.

## 4. Decide before reading the test outcomes

The primary mechanism endpoint is the **paired difference in native fresh-query success after one support, own history minus the matched donor history**. Use CloseToasterOvenDoor for development and fresh cases for confirmation. On RoboTwin report the equally weighted mean across all six held-out tasks and every task's estimate. First-attempt success measures transfer from offline training. Show cumulative ever-success only as a secondary measure of retry utility.

For confirmation, plan three independent student fits and 200 fresh cases per task, following the project's paired-case default. Share cases across fits. Report each fit, discordant paired counts and a 95% interval that resamples whole donor pairs within task, keeping methods, attempts and repeated draws together. Report between-fit variation separately. Use development-only discordance and throughput to check precision and price the full experiment before locking the bank. If the funded panel is smaller than needed, label it exploratory before opening it.

Proposed evidence threshold: the primary gain is at least **5 percentage points**, its paired 95% lower bound exceeds zero, and its sign agrees across fits. For a useful deployment advantage also require a positive gain over the separately trained memoryless policy at equal cost. Attribute a gain to *numeric reward* only if the reward-blind comparison supports it after checking visual and termination cues. If own history helps only on induced offsets, restrict the claim to that perturbation. If equally plausible unrelated histories perform just as well on the native tasks, report the measured transfer and retry performance and revisit the source histories before scaling.

First deliverable: run the existing frozen AD checkpoint on 32 fresh Toaster development cases, one support each. For every matched case run the own-history, donor-history and reset queries. This costs at most 128 episodes or 76,800 controls at H600. Report paired outcomes, donor coverage, actual controls and runtime per query. Use that table to price the trained controls and confirmation before scheduling them. Charge new work to its own allocation within the applicable budget.
