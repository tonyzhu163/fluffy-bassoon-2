# Seven failed openings in the native 90° rotation test

**The exact test passes 1,393/1,400 assignments (99.5%). Six streaming episodes used a visibly different realization of the reset scene. One frozen Base episode generated a different first proposal for a cause that the archived inputs cannot distinguish.** Same assigned start, same policy noise and even equal robot state can coexist with different observations. The first 16 pairs were seed 0, shard 000. The earliest failed assignment is number 65 in seed/shard order. The parent’s 28 field discrepancies independently match this audit in key, first sample and absolute error. The historical field `matched_prefix_histogram={"10":1400}` describes the available length. ## What failed at reset

The native LIBERO assignment and post-settle 25-dimensional robot state match exactly across all 1,400 pairs and all five repetitions. Within streaming, all repeated query-0 public EEF and policy EEF values agree. The matching keys include the ordered four episode slots, task, start, rep 0, adaptation seed, scene seed 0 in saved Base checkpoint keys/stream receipt, test split and rotation. Both arms use a strict-loaded frozen policy, the released CPU noise generator, identical chunk-seed formula, an uncompiled four-environment batch and ten settle controls. Full released schedules match apart from controller name/config. In the production streaming ledger query 0 used the identity estimate and unchanged EEF. Base stores episode seeds and the executed ten proposals, while stream also stores native query seeds and full-proposal hashes. Base does not retain a comparable full query digest or both camera inputs. [Audit and checks](audit.py) · [Pre-publication checks](checkpoints.json)

**Six drawer episodes.** For each of starts 44–49, all five Base prefixes and streaming seeds 1–4 are bit-identical. Streaming seed 0 alone differs at the original agent camera, its downsampled reader image and its live full-proposal hash. Streaming seeds 0, 1, 2 and 4 used PID 2690 on the same GPU UUID. Seed 0 was the only one whose worker retained this task across the boundary from shard 003 to shard 004. Its lane 0 had already reset on starts 28, 32, 36 and 40 before start 44. The other lanes have the corresponding one-, two- and three-index offsets. The next batch retains just two drawer lanes, for starts 48 and 49; the two fresh `goal_1` lanes pass. [Worker histories](batch-context.json) · [Reset/image/query evidence](failed-start-repetitions.json)

The pinned simulator code explains how that scheduling difference changes the world. `EnvPool` retains a worker on the same task. On a hard reset, robosuite reloads the model. LIBERO's BDDL initialization appends another drawer-open property sampler to an environment-lifetime list. Reset seeds NumPy, then draws from every accumulated property sampler before sampling fixture placements. Fixtures are written to MuJoCo **model** body positions/quaternions. The released fixed init row restores **simulation state**. Sampled fixture model poses survive. The recorded `X[0]` only describes the robot. On CPU the actual cold and retained histories for starts 44 and 48 reproduced equal native init vectors, robot states and flattened simulation states alongside different fixtures and both different camera images. At start 44 the warm history gave seven property samplers versus three and moved the cabinet 6.37 mm and wine rack 17.50 mm. The agent view changed at 15,298 of 65,536 pixels, the wrist at 15,901. Start 48 produced eight versus four samplers and moved the same fixtures 6.58 and 7.12 mm. Transplanting cold fixture poses into the disposable warm CPU scene removed most of the pixel discrepancy; the underlying receipt includes its residual. The GPU archives contain streaming image hashes and batch histories, not the original fixture coordinates or pixel arrays. **Direct causal control on all six starts.** In a third disposable environment we replayed each retained slot history and removed exactly the four duplicate sampler entries immediately before the affected reset. All other native reset operations and seeds stayed the same. The sampler counts returned from 7 to 3 for starts 44–47 and from 8 to 4 for starts 48–49. Both full camera images matched the cold Base-style reset with zero differing pixels on **6/6 starts**. All six also recovered the cold fixture-body position array and flattened simulation state bit-for-bit. This intervention isolates a reproducible assignment difference upstream of model inference. It is not necessary to patch the benchmark to repair the evaluation. **One spatial episode.** Base seed 1 is the sole outlier against the other four Base and every streaming repetition. Its batch contains spatial starts 45–48; the other three members pass. All 10 spatial runs entered start 48 with a fresh task worker. Base seed 3 restored the usual trajectory on the same GPU and PID 2578 used by Base seed 1. Streaming reset images and full first proposals have one hash per start over its five repeats. The Base checkpoint and published trace agree bit-for-bit across complete trajectories for all lanes in this batch and the two drawer batches. Independent streaming five-command ledger means agree with published issued actions. This localizes the discrepancy to the generated trajectory, before readback. A historical change in the Base wrist/agent render, latent scene, preprocessing or inference still fits the available evidence. Its smaller magnitude alone cannot identify floating-point arithmetic as the cause. No necessary device-class or driver effect has been established. ## Midpoint camera control and later behavior

The released step advances physics, records robot state and speed, and then requests observations. The streaming bridge additionally requests a render after controls 5, 15 and subsequent midpoints, hides non-native observations from the VLA loop and passes the public image to its independent CPU reader. The first five-control update preserves identity. On 1,393 pairs the subsequent states 6–10 and speeds match with the different render schedules. In the seven failures the first proposals already differ before the midpoint. A controlled CPU replay on `10_3/44` and `spatial_0/48` changed only the render at control 5 while issuing the same ten recorded Base commands. Both schedules gave identical per-step flattened simulator states, 11 robot states, ten speeds, and both endpoint camera hashes on each fixture; robot states and speeds also matched the native archived tape used for that replay. This directly tests the extra observation in these fixtures. [Replay evidence](cpu-reset-inspection.json)

Within-arm exhaustive checks give 1/280 variable Base openings and 6/280 variable streaming openings. Across the ten possible seed pairs per start, 4/2,800 Base and 24/2,800 streaming comparisons differ. Across **whole episodes**, 2 Base starts and 10 streaming starts have distinct traces. Outside the failed openings, Base `goal_2/41` first differs at query 10; streaming `goal_2/41`, `goal_1/21`, `goal_1/47` and `goal_1/49` first differ at controls 10, 20, 20 and 40. Only `goal_1/21` changes success across repeats (one success at 122 steps versus four failures at 300). That episode passed its ten-control check. Across the seven flagged starts, neither arm changes success or unsafe across repeats. ## Hardware and result implications

Both production jobs used four NVIDIA GeForce RTX 4090s with disjoint UUID sets on different hosts, common runtime and checkpoint lock hashes, Torch 2.11.0+cu128, CUDA build 12.8, LeRobot 0.6.1, MuJoCo 3.8.1, robosuite 1.4.0 and hf-libero 0.1.5. Base `job-3icnvzsc0y7c`, streaming `job-hl6vn153l9d3`, both exited 0. All eight worker logs contain the strict weight-load confirmation. Base logs report an NVIDIA EGL renderer; streaming sets the mapped EGL ordinal and records it per shard. The attempt probes identify allocation ordinals, PCI and physical UUIDs. Neither probe records the loaded kernel driver version. Driver 580.159.04 belongs to a separate development qualification. The paper's archived PDF and release README do not give a production model/driver pin sufficient for a historical hardware-identity claim. [Production receipts and runtime](hardware-and-bounds.json) · [Development qualification](../RUNTIME.md)

The archived grids have Base 0/1,400 successes and 1,005 unsafe, streaming 401/1,400 successes and 375 unsafe. Of the seven flagged pairs, Base has 0 successes and 7 unsafe; stream has 1 success and 1 unsafe. Holding the other 1,393 rows fixed and allowing every flagged binary outcome in either arm to take either value gives streaming success IQM **0.18429–0.19286**, Base **0**. Unsafe IQM **0.19857–0.20714** for streaming and **0.83429–0.84286** for Base. These are sharp point-estimate sensitivity bounds conditional on those fixed rows. They describe possible changes to the point estimates. A rerun that changes additional companion rows can fall outside these bounds. [Sensitivity calculation](hardware-and-bounds.json)

**Decision.** Preserve all original rows, record the seven failed openings and keep them flagged. The preregistered equality test needs no fitted tolerance. Recreate the original Base worker context on a baseline-class 4090, capture complete inputs and compare three native batches (12 assignments per arm, including companions). The spatial historical Base input cannot be reconstructed from its trace alone. If independent live inference fails to reproduce it, give the new matched comparison and historical fidelity separate verdicts.
