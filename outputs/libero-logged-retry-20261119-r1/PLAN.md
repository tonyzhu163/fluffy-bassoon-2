# What is a counterfactual retry worth?

Use the existing menu02 native LIBERO-Pro2.0 rollouts. Fix two executable choices, default and original pacing, before fitting. The stationary π0.5 always generated the practice with default control. A fitting or development history is a task, a support reset and a hidden BASE/S20 condition followed by a different query reset. Each panel contains eight task IDs, two support poses per task, and both conditions. Panels have disjoint tasks. The two physical alternatives within a query use the same reset and noise. They are potentially stochastic single draws. All 32 development rows, including double failures and ties, count. This is retrospective reuse of known development outcomes. Official test tasks stay sealed.

Use one binary-success head per candidate on the archived two-layer history transformer. Match initialization, optimizer, loss, update count, public features and test-time choices between supervision arms. The history is the first 80 charged controls of the practice plus its final public native success bit, available at retry time. The query is the current frozen visual feature and state. Train retained and empty histories together, and separately fit the same architecture with only current observations. Both variants minimize binary cross-entropy on observed labels only. No hidden condition, other candidate's label, oracle choice, or normalization from excluded histories enters fitting. A fair coin chooses which physical label can be seen in the logged arms with propensity 1/2, independently per fitting row. Retain logged failures.

At fixed histories expose one or both labels for all 32 fitting cases (64 versus 96 total episodes). At equal collection cost use 24 one-label cases or 16 two-label cases (48 episodes each, counting supports). For each task randomly pair one BASE and one S20 case at distinct reset IDs for the full-branch subset, then add one of the two remaining cases for its nested 3-case logged subset. Use four predetermined logging/subset seeds (101–104) crossed with two model seeds (41 and 42). Report actual charged controls in addition to episode counts. These are counterfactual data-acquisition costs on already collected rollouts. All predictors choose before either development query result is scored. Score native success, separately trained current-only, the same reader with empty support or opposite-condition support at matched task and pose, the existing public lag rule, the fixed native motor, and the best measured alternative per case. Report task-level results and paired gains/losses. Variation across logging and fitting seeds describes sensitivity, not independent replication. CPU computation only.

Further collection would use the same randomized logging scheme and a randomly assigned paired-audit subset on fresh physical starts. The development data inform motor coverage and disagreement; the number of windows or counterfactual relabelings cannot justify a transfer sample size.
