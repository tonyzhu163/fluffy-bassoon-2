The raw `memory_reset` intervention is specifically a recurrent-cache reset. Because the persistent controller retains `reset_each_episode=false`, direct previous-noise/reward inputs survive the boundary. The independently trained episode-reset controller clears both cache and previous feedback, while retaining within-episode recurrence and its episode clock. Reward blindness zeros reward input while retaining other history. These controls answer different questions; neither reset condition is described as memoryless. Actual case pairing does not make stochastic action draws common random numbers.

Possible explanations include conservative optimization movement, few valid decisions per update, sparse successful feedback, the steering interface's task-dependent authority and source-case difficulty. These remain hypotheses. Existing logs do not identify a cause or prove that more data, another memory architecture, or a new motor would fix it.
